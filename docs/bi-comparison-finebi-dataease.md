## 0. 结论摘要（TL;DR）

1. **三者不在同一赛道**：FineBI 是商业自助分析平台（指标驱动、企业级治理）；DataEase 是开源轻量
   可视化 BI；**APIBridge-BI 是数据交换平台内的"表单数据展示层"**（把已接入的业务表/工作表
   做成"当前状态"看板）。功能广度 FineBI ≫ DataEase > APIBridge-BI，但这不等于我们的场景输——
   三者面向的数据量级、使用者与接入成本完全不同。
2. **性能差异由架构决定且差 2~4 个数量级**：FineBI/DataEase 面向数仓大表（SQL 下推/本地抽取引擎，
   单表百万~亿行）；我们面向业务表单（**单源 ≤10 万行硬上限**，全量拉取内存聚合）。
   但在"小数据量 + 高频刷新 + 多看板"的展示层场景，我们**读预聚合桶（毫秒级、零源库压力）反而
   优于两者**的直连查询。
3. **两个独特优势是它们没有的**：① 与交换管道**同源**（连接/表单/字段字典/探针验证同一份配置，
   零重复录入）；② **agent 可配置可验证**（`skills/bi-dashboard` + 管理 API，唯一一个能由
   AI agent 从零建看板并经三级门禁自审的产品）。
4. **建议**：不做通用 BI 的追赶（追功能全=烧钱且无差异化）；优先补三件高性价比能力——
   **DB 源 SQL 下推聚合、增量拉取、行列权限**；订阅/移动端等用平台既有能力（调度/webhook/响应式）
   组合替代，不新造。

## 3. 性能差异（架构决定，附我方实测）

| 维度 | FineBI | DataEase | 我们（实测） |
|---|---|---|---|
| 计算位置 | 本地引擎（抽取）/ 数据库（直连） | 数据库（下推）/ 内置引擎（抽取）/ Calcite（联邦） | **应用内存（Python）** |
| 数据搬移 | 抽取一次性 + 增量 | 抽取按调度 | **每分钟全量拉取**（这是最大瓶颈） |
| 查询响应 | 引擎内计算，快 | 下推或引擎内，快 | **读预聚合桶，毫秒级**（实测查询无源库压力） |
| 单源上限 | 千万~亿级（未核实） | 百万~千万级（机制核实、数字未核实） | **10 万行**（硬上限，拉取前拦截） |
| 高频刷新成本 | 抽取按调度（分钟~小时） | 同 | **每分钟拉全量 × 指标数**（60s TTL 行缓存去重，多指标共享一次拉取） |
| 并发 | 集群扩展 | 取决于后端引擎 | 单进程；读桶无锁竞争（展示层场景足够） |
| 典型不可用场景 | —— | —— | 明细大表逐行分析、即席任意维度查询、TB 级 |

**关键判断**：我们的性能瓶颈在"全量拉取 + 内存聚合"，不在查询。因为①读桶毫秒级；②60s TTL
按 `连接:表单` 维度去重（同一表单的 N 个指标共享一次拉取）；③快照保留 60 桶自动清理。
在"表单级数据量（<10 万行）+ 分钟级新鲜度"这个场景，我们是**架构上合适**的；硬要撑数仓
规模则需要改架构（下推/增量），那是另一个产品的工程量。

## 4. 优缺点总结

**FineBI**
- 优：功能最全（自助分析、指标中心、治理、移动、订阅）；大客户生态与实施体系成熟。
- 缺：闭源商业化成本高；平台重（部署/运维/学习曲线）；对"平台内嵌展示"场景过重且无法
  与我们的交换管道共享配置。

**DataEase**
- 优：开源免费、部署极轻（1C2G）；数据源覆盖国产库全；视觉现代；计算字段/自定义分组/
  快速计算/72×36 画布均为一手借鉴来源（合规：只借鉴设计不复制代码）。
- 缺：高级能力受许可门禁（X-Pack）；中文文档偏营销、引擎细节稀疏；跨库依赖 Calcite 引入的
  复杂度；与本平台的连接体系完全割裂（要重复配一遍数据源与凭证）。

**APIBridge-BI**
- 优：① 与交换管道**同源**（凭证/字段字典/探针验证一体，零重复配置）；② **agent 可配置可自审**
  （唯一能由 AI 从零建看板的产品）；③ 快照语义天然匹配"当前状态"看板（生产运行管理即是）；
  ④ 读桶查询快、零源库压力；⑤ 零额外中间件（不需要 Doris/Calcite/独立服务）。
- 缺：① 单源 10 万行上限（大表不可用）；② 无自助拖拽分析、无行列权限、无订阅/预警、无移动 App；
  ③ 图表样式深度有限；④ 单人维护、单机部署。

## 5. 建议

### 5.1 定位建议（最重要）
**不做"通用 BI"的追赶**。三者对比的正确读法是：FineBI/DataEase 解决"把数仓数据交给分析师自助分析"；
我们解决"把已接入的业务表单交给操作员做当前状态监控，且能由 agent 规模化配置"。后者的差异化
（同源、agent、快照）比功能数量重要。若为对标 FineBI 而堆自助分析/权限/移动端，投入大且每个
方向都有成熟产品，得不偿失。

### 5.2 建议做（按性价比排序）
1. **DB 源 SQL 下推聚合**（最高杠杆）：form 源为 DB 表时，把 `SUM/GROUP BY/筛选` 下推为 SQL 执行，
   只取聚合结果——直接解除 10 万行上限对 DB 源的限制（HAP 源保持快照）。
2. **增量拉取**（快照的第二形态）：按主键/时间水位线只拉新增行（HAP 按 rowid、DB 按自增/时间列），
   把"每分钟全量"成本降到与增量成正比。
3. **行列权限**：复用平台 `auth-management` 域做看板级/卡片级数据权限——多角色场景的刚需，
   不引入新体系。
4. **图表样式按需扩**：跟随真实需求（不追求对齐 FineBI 的样式深度）。

### 5.3 建议不做 / 用既有能力替代
- **不做**：分布式/集群、拖拽 OLAP 自助分析、移动 App、水印审计——与定位不符。
- **替代**：订阅/预警 → 平台 `scheduler` + `webhook` 组合（可拼"定时截图推送"）；
  公共分享 → 投放页 URL 加**受限令牌**（小改造即可，收益明确）；
  同环比 → 保持不做（快照源无业务时间轴，DataEase 靠"时间回调一年取数"实现，与我们语义不符）。

### 5.4 一句话结论
**功能上：FineBI > DataEase > 我们；但在"交换平台表单展示层"的坐标里，我们的独特优势
（同源/agent 可配置/快照语义/零依赖）三者皆无——保持定位、补齐下推与增量两块短板、
其余按需借力平台既有能力，是正确的演进路线。**
