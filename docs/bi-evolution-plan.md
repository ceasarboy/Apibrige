# BI 大演进方案：对标并超越 DataEase

> 输入：用户 2026-09-27 拍板——「对标 DataEase 水平尽可能超越它；提升单源上限；
> 增加自助拖拽分析；评估单进程对「同时投放 + 数据分析」的影响；增加明细大表逐行分析、
> 即席任意维度查询、TB 级；四条建议（下推/增量/权限/样式）全部采纳」。
> 依据：`docs/bi-comparison-finebi-dataease.md`（三方对比）+ 本方案的并发实测。

## 0. 并发实测（先回答"单进程是否影响投放与分析的并行"）

**方法**：SQLite 造 9.5 万行大表（贴近现上限）→ form 指标全量聚合进行中，用探测线程
持续打投放页用的轻查询端点（读桶），统计延迟。

| 场景 | 平均延迟 | 最大延迟 | >1s |
|---|---|---|---|
| 基线（无重任务） | 12ms | 64ms | 0 |
| **9.5 万行全量聚合进行中（全程 1.2s）** | 19ms | **301ms** | 0 |
| 大表明细查询（0.14s）进行中 | 14ms | 77ms | 0 |

**结论**：
1. **当前规模下单进程不构成阻塞**——9.5 万行聚合 1.2s，投放查询只抖动到 301ms；
2. 聚合耗时随行数线性增长（百万行 ≈ 12s+），**上限提升后必须先做"计算移出事件循环 + 在飞查询限流"**（P5 前置到 P3 同步做）；
3. 实测暴露的**真瓶颈不在服务端并发，而在明细链路**：服务端 0.14s 回传全量 9.5 万行，
   前端 `DetailTable`（已去分页改滚动）会**全量渲染 DOM**——浏览器端必崩。这坐实了
   "明细大表逐行分析"必须先做**服务端分页 + 前端虚拟滚动**（P1）。

## 1. 六个方向 × 技术路线

| 用户方向 | 路线（核心决策） | 承接期 |
|---|---|---|
| 单源上限提升 | **DB 源聚合下推 SQL**（不拉行）+ HAP 源增量拉取；上限从"10 万行硬闸"变为"源库能力" | P3 + P4 |
| 明细大表逐行分析 | **明细服务端分页/过滤/排序**（DB 源下推 `WHERE/ORDER/LIMIT`；HAP 用 getFilterRows 原生分页）+ 前端虚拟滚动 | P1 |
| 即席任意维度查询 | **查询服务**：任意维度组合即时聚合（DB 源下推 GROUP BY；结果可暂存为"临时卡片"） | P2 |
| 自助拖拽分析 | 新「分析工作台」页：维度/度量拖拽 → 即时出图（复用 18 图表渲染），可一键"另存为看板卡片" | P2 |
| TB 级 | **数据不落我方**：明细分页、即席聚合、看板聚合全部下推到源库执行——源库有多大就能标多大；可选内嵌列存（DuckDB）作为"无 DB 源/HAP 大表"的加速层（评估项） | P3 落地即具备 |
| 单进程并发 | 聚合与下推查询走线程池（不占事件循环）+ 在飞长查询限流 + 调度聚合可配置独立进程 | P5（与 P3 同步硬化） |

**架构原则（不变）**：数据在源端，计算尽量下推；我方只存"预聚合桶"与"结果缓存"，
不落原始数据。TB 级由源库承担——这是"交换平台"定位下与 DataEase（需外置 Doris 容器）
最本质的路线差，也是**零新增中间件**的超越点。

## 2. 分期与范围（每期可独立交付验收）

### P1 明细服务化（add-bi-detail-query）——明细大表逐行分析 ✅ 已完成（2026-09-27）
- 服务端：`/bi/form-rows` 分页/排序/关键字（DB 源分页/升序下推=每页 page_size+1 行探测
  `has_more`，不拉全量；HAP/无法安全下推的能力在 60s 缓存内处理并标 `fallback`）
- 前端：明细卡工具条（搜索/排序字段/升降序/页码）+ 单页 200 行（**偏差记录**：
  虚拟滚动经评估不必要——200 行/页 DOM 已可控，原问题"全量 DOM 渲染"由分页解决）
- 验收：**实测 20 万行首屏 56ms / 第 500 页 132ms / 最深页 233ms（<300ms ✓）**、
  旧调用 3ms 兼容、`scripts/bi_detail_paging_check.py` 8 项全过、914 passed
- **偏差记录**：① 安全策略禁止动态 SQL 拼接（Mimosa 拦截）——关键字过滤与 desc 排序
  降级内存并标记，P3 聚合下推时统一；② COUNT 未下推——用 `has_more` 探测替代精确 total
  （大表 COUNT 亦慢），降级路径返回精确 total；③ HAP 原生分页留待 P4 一并做

### P2 分析工作台（add-bi-adhoc-analysis）——**已完成（2026-09-29 归档）**
- 后端（a11b18a）：`POST /bi/adhoc/query`——{connection_id, form_key, chart_type,
  dimensions[], measures[], filters[], computed[], top_n, sort, format} → 即时聚合 +
  `{engine, fallback_reason, truncated, elapsed_ms, defn, data}`；不落库；DB 源下推
  GROUP BY、HAP/不可下推走内存快照并如实标注；校验与输出复用定义保存/格式化链路
- 前端（2cd423b）：新页 `/bi/analysis`——字段树 + 维度/指标双槽（原生 HTML5 拖拽 +
  点击双通路）、即时出图（复用看板渲染器）、引擎标签、一键「另存为看板卡片」（+ 可选摆放）
- 验收：**引擎开销 ≤500ms**（1/2/3 维与无维度实测 5~70ms；口径校正见下）、
  拖拽到出图全流程（`scripts/analysis_ui_check.py` 13 项）、另存后看板可见且
  **卡片桶值与同参数即席查询逐项一致**（101 组）
- **偏差记录**：原验收"任意维度组合 <1s"实测在 SQLite 无索引 100 万行上不成立——
  同一条 GROUP BY 的**裸 SQL** 2~3 维就要 1.2~1.7s（源库成本与平台无关），
  故改为"引擎开销 = 接口耗时 − 源库裸 SQL 地板 ≤500ms"（design §7.1）

### P4 增量拉取（add-bi-hap-incremental）——**已完成（2026-09-29 归档）**
- 前置：**真实端点探针**证明服务端支持 `filters`+`sortId`，`utime > 水位线`（严格大于）
  可精确圈"新增 + 变更"；并踩到 `filterControls` 参数名被静默忽略
- 实现：适配器 `get_rows_since`（严格/含等两模式）+ `bi_sources` 快照存储与**两段式增量**
  （严格大于取真增量 → `ge 水位线` 客户端差集得"同秒边界集"，超 2000 行即跳过）
  + 定期全量对账（默认 600s）+ 规模闸（默认 2 万行，小表保持全量语义）+ 环境变量覆写
- 验收（真实 api.mingdao.com 全过）：稳态增量 **2.04% < 5%**（144 行表 +3 变化）→
  拉 3 行；合并快照与源端**逐行零差异**（147=147）；同秒新行由边界刷新救回；
  删除行按设计滞留（对账清除）；让渡语义写进 `GET /bi/form-rows` 的 `snapshot` 字段
- **偏差记录**：原"2s 重叠窗口"实测会把**水位线同秒的行整批重拉**（本表 144 行同秒 →
  增量=整表）→ 改两段式；服务端同字段多条件是 OR（`ge AND le` 返回整表）→ 边界集只能
  客户端差集。详见 `archive/2026-09-29-add-bi-hap-incremental/design.md` §6
- 非目标：同步引擎的 HAP 增量（另立变更）、删除实时感知、超 10 万行 HAP 工作表

## 3. 超越 DataEase 的差异点（演进后成立）

| 差异点 | DataEase | 我们（P1-P3 后） |
|---|---|---|
| 大表引擎 | 需外置内置引擎（Doris 容器，许可门禁） | **零新增中间件**：下推源库 + 可选内嵌 DuckDB |
| 接入成本 | 数据源/凭证重新配置 | **与交换管道同源**（零重复配置） |
| Agent 能力 | 无 | skill + API 全流程可配置可自审（MCP 生态可直接驱动） |
| 明细大表 | 有限（组件性能依赖前端） | 服务端分页 + 虚拟滚动（20 万行级流畅） |
| 即席分析 | 有（组件级） | 有（分析工作台 + 另存为卡片） |
| 部署 | 容器编排（多组件） | 单进程 FastAPI（同平台） |

## 4. 风险与对策

- **下推的方言差异**（SQLite/MySQL/PG/Oracle）：聚合 SQL 生成走适配层方言字典；
  拿不准的写法**回退内存路径**（保正确性优先）；
- **HAP 源无法下推**：增量（P4）+ 分档上限提示（如 >20 万行建议换 DB 源）；
- **前端虚拟滚动**：引入成熟的 `rc-virtual-list`（antd 内置依赖，零新包）；
- **调度聚合独立进程**：默认关闭（保持单 worker 简单），大表部署时开启。
