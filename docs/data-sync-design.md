# 数据同步业务逻辑（v1 梳理）

> 本文是项目的业务基准：打通 API 只是手段，**数据在源与接收方之间可靠同步**才是目的。
> 验收标准 = 三种变更（新增/变更/删除）能按配置正确落到目标，而不是"API 通了"。
> 最后更新：2026-09-06

## 一、同步的业务定义

```
源系统                       APIBridge                        目标系统
┌──────────────┐    读取      ┌──────────────┐    写入     ┌──────────────┐
│ API / 表单 /  │ ──────────→ │  字段映射      │ ─────────→ │  API / 表单 / │
│ 数据库        │    增量水位   │  格式/定义转换  │   upsert/   │  数据库       │
│              │              │  冲突策略      │   delete    │              │
└──────────────┘              └──────────────┘             └──────────────┘
```

三种必须支持的变更（CDC 语义）：

| 变更 | 源侧表现 | 目标侧动作 | 当前状态 |
|---|---|---|---|
| **新增 INSERT** | 新行出现 / webhook 推送 | INSERT（或 upsert） | ✅ 已实现（手动运行 / webhook / cron 轮询 / 增量水位） |
| **变更 UPDATE** | 行内容变化（有 updated_at 时增量可见） | UPDATE（upsert 覆盖） | ⚠️ 部分：有增量字段的源可捕获；无增量字段的源无法发现变更 |
| **删除 DELETE** | 源侧行消失 / 软删除标记 | DELETE（或软删标记） | ❌ 未实现——目前源删除后目标不受影响 |

## 二、现状矩阵（哪些路径已真实可用）

| 源 → 目标 | 新增 | 变更 | 删除 | 说明 |
|---|---|---|---|---|
| REST API → REST API | ✅ webhook / cron / 手动 | ⚠️ 源需可查询 | ❌ | 三场景冒烟已验证 |
| DB → DB | ✅ 增量水位 + upsert | ⚠️ 需增量字段 | ❌ | Oracle/MySQL/PG/SQLite |
| DB → REST API | ✅ | ⚠️ | ❌ | |
| REST API → DB | ✅ webhook | ⚠️ | ❌ | Oracle 真库已验证 |
| **明道云表单 → 任意** | ❌ HAP 适配器骨架未接线 | ❌ | ❌ | 用户真实场景，最高优先 |
| **任意 → 明道云表单** | ❌ | ❌ | ❌ | 同上 |

其他已就绪的配套能力：
- 字段映射：探针 Schema 推断 + 同名退化草案 + 人工确认（待确认清单）
- 字段格式/定义转换：transform（string/int/float）+ 确定性类型校验
- 冲突策略：skip / overwrite（按内容哈希）
- 增量水位：incremental_field + last_sync_value（成功后推进）

## 三、缺口与实现方案（按优先级）

### P1：明道云表单作为源/目标（用户真实场景）

明道云开放 API（V1，已实测鉴权方式：query 参数 appKey/sign）：

| 动作 | 端点 | 说明 |
|---|---|---|
| 读字段定义 | POST /v1/open/worksheet/getFields | 探针 infer 的表单源支持（字段 ID→名称/类型） |
| 读行（含过滤） | POST /v1/open/worksheet/getFilterRows | fetch_data 接线；支持视图/过滤 |
| 写行 | POST /v1/open/worksheet/worksheetRow/createRows | push 接线 |
| 更新行 | POST /v1/open/worksheet/editRow | upsert 变更 |
| 删行 | POST /v1/open/worksheet/deleteRows | 删除同步（目标=明道云时） |

实现要点：
- HapV3Adapter.fetch_data/push_data 按 worksheet_id + 视图对接上述端点
- 明道云字段以 fieldId 标识，需用 getFields 建立 字段ID→名称 映射，
  映射草案的"字段格式和定义"即来自这里（名称/类型/必填）
- appKey/sign 已由适配器转为 query 参数（复用现有鉴权）

### P2：删除同步（三种可选机制，按源能力选择）

| 方案 | 前提 | 复杂度 | 说明 |
|---|---|---|---|
| A. 水位+主键比对 | 源可全量拉主键 | 中 | 每轮同步记录源主键快照，下一轮对比：源消失 → 目标删除。数据量大时慢但可靠 |
| B. 源 webhook 删事件 | 源支持推送删除 | 低 | 明道云/带 webhook 的系统走此路 |
| C. 软删除标记 | 源有 is_deleted 字段 | 低 | 过滤条件取 is_deleted=0，目标执行软删/硬删 |

建议：先实现 A（通用），配置项 `delete_sync: off|on`（默认 off，防止误删）。

### P3：变更捕获增强（无增量字段的源）

- 无 updated_at 的源只能全量比对：按主键+内容哈希对比目标，差集更新
- 可复用 conflict 的 compute_record_hash，加 `sync_mode: "full_compare"`

### P4：同步结果的可观测

- 每轮同步的运行摘要：新增 N / 变更 M / 删除 K / 跳过 S / 失败 F（写入执行日志与看板）
- 让"数据传输同步"的验收标准可量化

## 四、验收口径（每个同步任务上线前）

1. 探针 L2/L3 通过（真实转换 + 真实写读比对）
2. 人工在待确认清单批准（映射、方向、冲突策略、删除开关）
3. 首轮同步：源 N 条 → 目标 N 条，执行日志齐全
4. 变更演练：源改 1 条/删 1 条/加 1 条 → 再次同步 → 目标与源一致
