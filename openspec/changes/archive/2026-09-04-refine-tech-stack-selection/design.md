## Context

本项目为新建项目，无遗留代码。初步方案（见 docs/apibridge_design.md）已确定技术栈：FastAPI + PostgreSQL + Redis + RabbitMQ + Celery。本设计聚焦"存储层职责分工"与"传输模式切换"两个架构决策，这是双API桥接平台的核心，需在编码前定案。

约束：内网离线部署、中文文档、遵循 CLAUDE.md（简单优先、目标驱动）。

## Goals / Non-Goals

**Goals:**
- 明确 Redis/PostgreSQL/RabbitMQ 三者职责边界，避免职责重叠导致的一致性问题
- 提供同步与异步两种传输路径，按任务配置切换
- 数据库连接器具备缓存与批处理能力，降低 DB 压力
- 架构可测试，每个决策点有明确的验收标准

**Non-Goals:**
- 不设计前端界面（后端架构为主）
- 不设计多租户隔离
- 不设计 Redis 高可用（单节点起步）
- 不设计协议层细节（gRPC/GraphQL 后续迭代）

## Decisions

### 决策1: Redis 不做主队列，仅承担四项辅助职责

**选择**: RabbitMQ 作为异步任务主队列，Redis 仅负责幂等去重、分布式锁、API限流、热缓存。

**理由**:
- RabbitMQ 提供 ACK 机制、死信队列、消息持久化，适合可靠传输
- Redis 持久化（RDB/AOF）有窗口期，极端故障可能丢消息
- 职责分离降低单点故障影响面

**备选方案**:
- *Redis Stream 做队列*: 延迟更低（μs级），但持久化弱、无死信队列。拒绝原因：数据桥接场景对可靠性要求高于延迟。
- *Kafka 做队列*: 吞吐最高，但运维重、内网部署资源占用大。拒绝原因：本项目规模不需要 Kafka 级吞吐。

### 决策2: PostgreSQL data_buffer 作为真相源

**选择**: 所有中转数据（无论同步/异步）都写入 PostgreSQL data_buffer 表，Redis 不存储中转数据。

**理由**:
- PostgreSQL 提供事务保证，异常时数据可回溯
- data_buffer 的 JSONB 字段灵活适配不同数据结构
- Redis 可从 PostgreSQL 重建，反之不可

**备选方案**:
- *双写 Redis + PostgreSQL*: 性能略高，但需处理双写一致性，复杂度增加。拒绝原因：CLAUDE.md 要求简单优先。
- *纯 PostgreSQL（无 Redis 缓存）*: 最简单，但失去热缓存能力。拒绝原因：表结构等元数据频繁查询需缓存。

### 决策3: 同步模式在 FastAPI 路由内完成全链路

**选择**: 同步模式下，"拉取源→写 data_buffer→转换→推送目标→更新状态"在单个 HTTP 请求内完成，不投递 RabbitMQ。

**理由**:
- 避免队列往返延迟，P99 目标 <1秒可达
- 调用方可同步获得结果，简化集成

**备选方案**:
- *全部走异步*: 架构统一，但实时场景延迟高（秒级）。拒绝原因：部分场景需实时反馈。
- *同步模式也写队列但立即消费*: 增加一次序列化/反序列化开销。拒绝原因：无收益的复杂度。

### 决策4: 异步模式"先持久化再投递"

**选择**: 异步模式下，数据先写 PostgreSQL data_buffer（status=pending），再投递 RabbitMQ，立即返回任务ID。Worker 消费时更新 data_buffer 状态。

**理由**:
- 持久化优先保证数据不丢（即使 RabbitMQ 故障）
- 投递失败可由扫描 pending 数据补偿
- PostgreSQL 是真相源，RabbitMQ 仅作通知通道

**备选方案**:
- *先投递 RabbitMQ 再持久化*: 延迟更低，但 RabbitMQ 故障时数据丢失。拒绝原因：可靠性优先。
- *仅投递 RabbitMQ 不持久化*: 最快，但无回溯能力。拒绝原因：不符合真相源原则。

### 决策5: auto 模式按数据量阈值切换

**选择**: auto 模式下，预估数据量 <100 条用同步，≥100 条用异步。阈值可配置。

**理由**:
- 100 条以内同步处理 P99 可控制在 1 秒内
- 超过 100 条同步处理易超时，异步更可靠
- 阈值可配置，适应不同硬件环境

**备选方案**:
- *按数据字节数判断*: 更精确，但需预计算大小，增加开销。拒绝原因：条数足够简单。
- *固定全异步*: 简单，但小数据量延迟高。拒绝原因：体验差。

### 决策6: fallback_to_async 默认关闭

**选择**: 同步失败转异步为可选开关，默认关闭。

**理由**:
- 默认关闭保持行为可预测（失败即失败，由调用方决策重试）
- 开启后增加异步路径依赖，调用方需处理"部分同步部分异步"的混合结果
- CLAUDE.md 要求不过度设计

**备选方案**:
- *默认开启*: 提升成功率，但行为不可预测，调试困难。拒绝原因：违反简单优先。
- *不提供此开关*: 极端简单，但部分场景确需降级。拒绝原因：灵活性不足。

### 决策7: 数据库连接器三级缓存

**选择**: 表结构缓存 Redis（TTL 1h）+ 增量同步批量预取（batch_size 默认 1000）+ 写入缓冲（阈值或超时 5 秒提交）。

**理由**:
- 表结构变更低频，1 小时缓存显著减少 DB 查询
- 批量预取减少 DB 往返，避免内存溢出
- 写入缓冲提升吞吐，超时保证延迟上限

**备选方案**:
- *不缓存表结构*: 每次查 DB，简单但压力大。拒绝原因：元数据查询频繁。
- *全量加载到内存*: 最快，但大表内存溢出。拒绝原因：不安全。

## Risks / Trade-offs

- **[Redis 单点故障]** → 幂等去重/锁失效，可能重复处理。缓解：PostgreSQL 兜底校验（data_buffer 状态检查）；后续迭代 Redis 主从。
- **[同步模式阻塞 worker]** → 高并发同步请求拖慢服务。缓解：FastAPI 异步 IO + 超时控制 + auto 模式自动转异步。
- **[auto 阈值不适配]** → 100 条阈值在慢网络下仍超时。缓解：阈值可配置，按实际环境调整。
- **[PostgreSQL 写入瓶颈]** → 高吞吐异步场景 data_buffer 写入压力大。缓解：批量写入 + 索引优化 + 后续可分表。
- **[混合模式复杂度]** → 同步/异步两条路径增加约 20% 代码量。缓解：共用转换/推送组件，仅传输层分流。

## Migration Plan

本项目为新建，无需迁移。部署步骤：
1. 初始化 PostgreSQL schema（含 data_buffer、execution_logs 等表）
2. 启动 Redis、RabbitMQ 服务
3. 启动 FastAPI 服务（同步模式入口）
4. 启动 Celery Worker（异步模式消费）
5. 启动 Celery Beat（定时任务）
6. 健康检查通过后接入业务

回滚策略：停服即可，无数据迁移风险（新建项目）。
