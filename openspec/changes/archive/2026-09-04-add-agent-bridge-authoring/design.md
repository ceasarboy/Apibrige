## Context

本变更建立在 `refine-tech-stack-selection`（存储分工与双传输模式）和 `add-management-ui-and-protocols`（管理界面与协议适配器）之上，前两者的核心架构决策不变。

约束：内网离线部署、无外网依赖、中文文档与注释、遵循 CLAUDE.md（简单优先、外科手术式修改、目标驱动）。

触发本变更的事实（均已实测复现）：

- 同步链路读取凭据不解密 → 带认证的桥接 100% 401（`api_client.py:33-34`）
- 适配器层与同步引擎是两套平行实现 → "探针通过"与"任务能跑"互不蕴含（`connections.py:165` 是适配器唯一生产调用点）
- `debug/proxy` 无鉴权、无目标限制、无响应体上限 → 不可被复用，只能收编
- 新建一条桥接需人工完成"选协议→试接口→猜字段→对映射"，这是平台使用中最大的一块人力成本

## Goals / Non-Goals

**Goals:**

- 让 LLM/agent 能驱动"联调"这个循环，并把产物变成可运行的桥接配置
- 把"调通了"定义为机器可复现的三级状态，消除假信号
- 人在环中：agent 无直接写库能力，一切经清单批准
- 顺带修掉让上述目标不可能成立的四个前置缺陷
- 服务端零模型依赖，内网离线包与生产镜像不变

**Non-Goals:**

- 不做平台内置模型调用（"AI 调试"按钮）
- 不做多租户与 RBAC（沿用既有非目标）
- 不引入迁移框架
- 不做映射智能推荐算法
- 不做大流量压测自动化

## Decisions

### 决策1：模型归属在驱动侧，APIBridge 服务端零模型依赖

**选择**：LLM 只存在于工程师本机的 agent（pi / Claude Code / Trae）里。APIBridge 提供的是模型无关的探针内核 + agent 接口。内网模型端点与 API Key 配在 agent 侧，不进代码、不进镜像、不进离线包。

**备选方案**：
- *平台内置调模型*：非工程师也能用，但离线包要装模型、要养 prompt 资产、要把 SSRF 面从内部工具升级成平台功能。
- *MCP server 内嵌进 APIBridge 进程*：省一跳网络，但生产镜像要装 `mcp` 依赖，与"离线交付最小化"冲突。

**理由**：这是唯一让「内网离线部署」这条硬约束完全不受影响的形态。将来若决定做内置（方案 C），本变更的探针内核与待确认清单可原样复用，不需改任何契约——所以现在不必为它预付复杂度。

### 决策2：探针与运行时强制同源

**选择**：`app/probe/prober.py` 不得自己发 HTTP。它构造与运行时完全一致的 `adapter_config`（含解密后的凭据、合并后的 header、变量解析后的 endpoint），交给 `ProtocolAdapterFactory.create(conn.protocol, config)`。同时 `route_transfer` 的 `_fetch_source`/`_push_target` 也改为走工厂，删掉 `api_client.py` 里的平行传输函数。

**备选方案**：
- *探针复用 `debug/proxy`（裸 httpx）*：实现最快，但探针通≠运行通，本变更的立身之本直接失效。
- *两边各自实现，靠测试对齐*：脆弱，正是现状。

**理由**：只有同源，"L2 已通过"才是可信信号。这一条同时兑现了 `protocol-adapters/spec.md:9` 里那句从未被满足的 MUST。

### 决策3：以三级验证取代"通了"

**选择**：

| 级别 | 名称 | 做什么 | 是否碰目标系统 | 用途 |
|---|---|---|---|---|
| L1 | `reachable` | 端点可达 + 认证有效 | 否 | 排除配置错 |
| L2 | `transform_verified` | 真实拉源数据（≤20 条）+ 真实转换 + 真实校验 + 目标契约比对 | **否** | 进待确认清单的门槛 |
| L3 | `e2e_verified` | 写入 1 条 → 回读 → `comparator` 比对一致 | 是，需人工授权 | 证明同步真的通 |

L2 的目标端"契约比对"= 校验映射输出符合目标 schema（数据库侧查 `get_table_schema`；API 侧用 L1 采样或用户声明的响应结构），不做写入。

**备选方案**：
- *单一"测试通过"布尔*：会给出假信号，用户据此上线后数据丢失。
- *L2 就直接真写一条验证*：未确认前向生产系统写数据不可接受。

**理由**：桥接的失败模式是静默的（少字段、类型退化、数组路径没进），布尔不够用；而 L3 单独分级让"要不要真写生产"这个决定权明确留在人手里。

### 决策4：agent 无直接建桥能力，一切经清单批准

**选择**：CLI **不提供**任何直接创建 `ApiConnection`/`FieldMapping`/`SyncTask` 的子命令。agent 的全部写入能力止于：`apibridge protocol apply` 把一个会话提交到 `pending_review`。只有人在清单页点“批准”，才在单个事务里建桥。批准时人可以直接改映射，但改动会触发重校验与必要时重跑 L2。

**为什么批准不开放给 CLI**：确认动作的意义在于“人看过了”。一个能在终端盲敲 `--yes` 的批准，会把这道闸门的语义从“人审”变成“人签名”，并丢掉清单页的三栏对照与 L3 二次弹窗。CLI 保留 `review list|show` 只读，够 agent 回报状态。

**备选方案**：
- *给 agent 一个 `protocol commit` 子命令直接建桥*：多一步就少一步人审，误建桥会直写外部系统。
- *给 agent 发的配置打 `status=draft` 标记，运行时忽略 draft*：需要改所有查询路径加过滤，且"忘记过滤"是静默故障。

**理由**：把"是否让这条桥开始写真实系统"这个不可逆决定，物理上留在人手里。清单同时天然是审计记录（谁、何时、批准了什么映射、探针达到几级）。

### 决策5：CLI 是 agent 的唯一入口，输出契约必须机器可读

**选择**：`python -m app.probe.cli` 是唯一面向 agent 的接口，子命令为 `probe`/`infer`/`draft`/`verify`/`protocol apply`/`session show`/`review list|show`。它只懂 HTTP、参数解析与输出格式化，不含业务逻辑；全部能力落在 `app/probe/` 与 `app/api/probes.py`。本期不做 MCP server。

agent-readable 三项硬要求：
1. `--json` 输出是**带 `schema_version` 的稳定契约**，字段一经发布不改名
2. 退出码区分：`0` 成功 / `2` 验证未通过 / `3` 被拒绝（鉴权、预算、状态不足）/ `4` 调用错误
3. 每个失败带 `next_action`，告诉 agent 下一步做什么（而不是一个异常堆栈）

协议特有参数（gRPC 方法名、GraphQL query、SOAP operation、Dubbo args）放进 `mapping_config["protocol"]` 子字典，不加新列。

**备选方案**：
- *MCP server 作主干*：要新增依赖与新进程，而 pi / Claude Code 本身就能用 shell 驱动 CLI，收益不抵复杂度。因探针内核与 HTTP 契约与宿主无关，将来新增 MCP 只是薄封装，故推后不损失任何设计。
- *CLI 内实现业务逻辑*：与服务端两套实现必漂移，且绕开鉴权与白名单。
- *CLI 进程内直接 import core*：无法远程，多一种运行模式要维护。
- *为协议参数加数据库列*：要迁移，而本期正是要避免引迁移框架。

**理由**：`mapping_config` 已是承载 `fields`/`validations` 的 JSON 容器，再加一个 `protocol` 键是零成本扩展，且探针与运行时读同一个对象。而「契约版本化 + 退出码 + next_action」这三件，是把 CLI 从“给人用的工具”变成“给 agent 用的接口”的全部成本。

### 决策6：`debug/proxy` 降级为底座，裸端点删除

**选择**：把 `app/api/debug.py` 的转发逻辑迁入 `app/probe/prober.py` 的 REST 路径，加上鉴权、目标白名单、响应体上限；`/api/v1/debug/proxy` 与 `/api/v1/debug/quick-proxy` 两个端点移除。前端调试页改为面向 `apibridge probe`，并标注为"联调探针"。

**备选方案**：
- *保留裸端点另加探针*：全项目最高危入口继续敞着。
- *给它单独加鉴权就留下*：仍是任意内网地址读写回显，只是多道门。

**理由**：能力上探针是它的超集，留两份只会让 agent 走错门。

### 决策7：安全边界 = 共享 token + 私网默认拒绝

**选择**：
- `APIBRIDGE_ADMIN_TOKEN` 保护 `/api/v1/*`（`/health`、`/metrics` 豁免）。FastAPI 依赖注入实现，不引框架。
- `APIBRIDGE_PROBE_ALLOWED_HOSTS`：探针目标必须命中；先解析 DNS，再拒绝回环 / RFC1918 / 链路本地 / 云元数据地址；重定向逐跳复校验。
- `APIBRIDGE_PROBE_MAX_BODY_BYTES`：响应体上限（现 `debug.py:99` 是全量回显，无上限）。

**备选方案**：
- *完整 RBAC*：与"不做权限体系"的非目标冲突，本期只是内部工具。
- *只做 token 不做目标限制*：agent 驱动下 SSRF 的可达面比人手动更大，必须一起收。

**理由**：token 解决"谁能用"，白名单解决"能对谁用"。交给 agent 之前两件事缺一不可。

### 决策8：映射草案 = agent 提议 + core 确定性校验

**选择**：agent 可以提交一份字段对应关系；core 用两端 schema 校验——源字段是否真存在于源样本、目标字段是否真存在于目标表/契约、类型转换是否可行、必填是否覆盖——并回传逐项通过/失败原因。agent 缺席时退化为同名+类型兼容自动匹配。

**备选方案**：
- *模型输出直接当映射用*：幻觉字段进生产，且没有任何地方能拦住。
- *只做纯静态同名匹配*：不需要 LLM，但私有 schema（如 HAP 字段是随机 ID）根本配不出来，等于放弃本变更价值。

**理由**：让 LLM 负责"猜"，让代码负责"验"。校验逻辑是确定性的，可单测、可离线、可拒绝。

### 决策9：前置修复只划"本功能成立所必需"这一条线

**选择**：本变更只修四件前置——① 同步链路解密（含密钥缺失明确失败、PUT 掩码值不覆盖原值）；② 适配器接入 `route_transfer`；③ compose 环境变量补 `APIBRIDGE_` 前缀并修部署文档；④ `init.sql` 由模型生成 + 一致性检查脚本。

**备选方案**：
- *顺手引入 Alembic*：正确但独立，会把本变更面积扩大到"数据库演进"整件事。
- *前置另开一个 change*：但 ① ② 不修，探针就是假信号，两件事逻辑上不可分。

**理由**：不夹带无关重构（CLAUDE.md「外科手术式修改」），但把"不做则本功能无意义"的项留在本变更内。其余上轮发现的问题（compose 之外的 metrics 500、前端 build、幂等键顺序等）不进本变更，另列清单跟进。

### 决策10：孤岛回收以"探针正好是它的使用者"为限

**选择**：接入 `sync_counter`/`sync_duration`/`api_calls`/`api_call_duration` 四个指标上报（探针与运行时共用）；`batch_fetch` 接入探针分页拉取；`data_hash` 补写入使冲突检测生效；删除 `WriteBuffer`（零引用，且 `_timeout_flush` 会 cancel 自身任务导致批次丢失）。`queue_depth`/`active_tasks`/`db_pool_size`/`test_runs`/`stress_qps` 本期不接。

**理由**：探针天然要测时延和调用量，接上即让 `alerts.yml` 里 4 条哑火规则复活，是顺路收益而非额外工程。其余留到"监控"专项。

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| 加 token 后现有前端与 307 例测试全挂 | 阻塞交付 | 前端加 token 输入 + axios 拦截器；`conftest.py` 统一注入测试 token；列为 task 2 的验收项 |
| 适配器接入 `route_transfer` 改动核心链路 | 回归风险 | 分协议逐个切（REST 先，向后兼容），每切一个补一条端到端用例；`sync_handler` 其余步骤不动 |
| L3 回读依赖目标系统提供查询能力 | L3 无法自动化 | L3 定义降级路径：无法回读时只做"写成功且目标返回 ID"，并在清单上明写 `L3_partial`，不谎称完整比对 |
| 目标白名单需要运维逐项配置 | 上手摩擦 | 提供 `ALLOWED_HOSTS=*` 显式危险开关并在启动日志大字告警，默认仍拒绝 |
| agent 反复探针打爆外部系统 | 对方限流/封禁 | 探针复用现有限流器，按 `target:{id}` 计；单次会话探针对同一目标默认 ≤10 次 |
| 探针会话堆积无人审 | 清单失效 | `expires_at` 默认 7 天自动 `expired`；列表默认只看 `pending_review` |
| gRPC/GraphQL 等协议实际能否用仍未验证 | 承诺过大 | 本变更只保证"探针与运行时同源"，不承诺协议完备性；L1/L2 结果即事实，跑不通就停在 probing |
| 共享 token 明文存 localStorage | XSS 泄 token | 管理后台为内网可信用户；后续 SaaS 阶段随 RBAC 一并换成短时效 token，本变更记为已知限制 |
| `--json` 字段改名会静默弄坏已有 agent 工作流 | agent 侧难以定位的失败 | 输出带 `schema_version`；契约测试钉住字段集；破坏性变更递增大版本号 |
| token 写在命令行 argv 被其他进程读到 | 凭证泄露 | CLI 只从环境变量/配置文件读 token，不提供 `--token` 参数；说明书明写此约束 |
| agent 循环失控反复探测 | 对端限流封禁、成本 | 会话预算（≤10 次/目标）之外再加全局探测 QPS 上限；耗尽返回 `probe_budget_exhausted` 升人工 |

## Migration Plan

本变更共 8 组任务、**88 个可独立验证单元**，偏大。按可独立上线与独立回滚切成三阶段，**每阶段交付一个完整可用的价值闭环**，允许在任一阶段边界停下：

| 阶段 | 内容 | 独立价值 | 停在此处的后果 |
|---|---|---|---|
| **Ⅰ 修通与收口** | 组 1 前置修复 + 组 2 安全（21 项） | 带认证的桥接第一次真的能同步；最高危 SSRF 入口关闭 | 无损失，本阶段自身就是 P0 修复 |
| **Ⅱ 联调闭环（无 LLM）** | 组 3 探针内核 + 组 4 清单 API + 组 5 前端（34 项） | 人在清单页上完成"探→推→校→比→批"；探针 HTTP 面可直接用 curl 驱动；离线可用 | agent 接入延后，但联调人力成本已降 |
| **Ⅲ agent 化与收尾** | 组 6 CLI/说明书 + 组 7 孤岛 + 组 8 端到端与文档（33 项） | 外部 agent 驱动完整循环（模型不进气泡）；告警与看板复活 | 前两个阶段成果不受影响 |

上线顺序（每步可独立验证，任一步失败不影响前一步）：

1. **前置修复**（解密 / env 前缀 / init.sql 生成 / 掩码回写）→ 验证：带 bearer 认证的 REST→REST 端到端跑通一次
2. **安全收口**（token + 白名单 + 删裸端点）→ 验证：无 token 一律 401；探针打内网元数据地址被拒
3. **适配器接入运行时链路**（先 REST，再按协议推进）→ 验证：新增端到端用例覆盖 sync/async/auto × REST 源/目标
4. **探针内核 + `probe_sessions`** → 验证：L1/L2 在离线可测（无模型）
5. **待确认清单 API + 前端页** → 验证：批准产生三张表的原子写入，驳回不产生
6. **CLI + 协议/CLI skill 文档** → 验证：一个外部 agent 会话从裸 URL 走到清单出现
7. **孤岛回收**（指标 / batch_fetch / data_hash / 删 WriteBuffer）→ 验证：`/metrics` 出现四个新指标，`alerts.yml` 规则有数据
